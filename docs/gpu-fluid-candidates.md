# GPU fluid-solver candidates

The renderer gate is a convincing, clean live liquid-light projection with independently controllable color material, credible oil/water interfaces and motion, and user-reviewed stills and video. The target includes demanding visual quality, interactive performance and 4K export. A GPU backend alone does not establish any of those outcomes.

**No GPU solver has yet been validated for the required oil-and-water projector behavior.** Experimental Sailfish two-component runs have executed on the Mac's Radeon and Intel GPUs and on a Windows NVIDIA GPU; their limitations and evidence are documented in the [binary-fluid study](../experiments/sailfish-binary-study/README.md). None of the candidates has demonstrated the requested projector appearance, sustained interactive performance, memory use or 4K export throughput. The current app shader and the four-independent-field experiment do not meet the renderer gate.

## Local GPU evidence

The Mac reports an Intel UHD Graphics 630, up to 1536 MB dynamic memory, and an AMD Radeon Pro 5300M with 4 GB VRAM. Both report Metal 3. A small native Metal arithmetic kernel was dispatched and read back on each device using [`metal-probe.swift`](../experiments/liquid-fluid/metal-probe.swift). This verifies basic compute and explicit device selection only. The earlier browser fluid study reported the Intel GPU, not the Radeon; it is not a Radeon fluid-performance benchmark.

Runtime discovery must enumerate adapters and check the backend, features, resource limits and actual workload performance. Device model names are useful for reporting test results, not prerequisites or substitutes for capability checks. Experiments have also executed on the Windows NVIDIA GPU; see the [optical study](../experiments/optics-next/README.md). Separate tests of devices do not demonstrate simultaneous multi-GPU operation. Mac GPU dispatches have been suspended following reported driver errors described in that study.

## Taichi Metal observations

An isolated run of the upstream dense numerical solver at `fe49e3f609b2038cbf93c8bd453ffc5c2bf98e4c` selected Metal and shortened the run to two steps. With Python 3.11.12 and Taichi 1.7.2 it failed at `M.from_numpy(M_np)` with `Type u64 not supported` before a fluid step. With Python 3.9.25 and Taichi 1.0.2, the original 131³ input failed during Metal shader compilation due to an integer stride overflow. A separate 32³ synthetic input failed at the same transfer with an unsupported `int64_t` error. The numerical solver was not changed; these are failed experiments, not evidence of a working backend. Detailed environment and equation findings are recorded in [issue #5](https://gitea.gnomatix.com/gnpng/org/issues/5#issuecomment-5556).

## Quality and performance evaluation

- Validate actual separate material/color states and coupled interfaces, conservation and pressure-driven plate displacement, then compare projected appearance and motion against the supplied photograph and video references. Optical absorption, refraction, illumination and projection must be evaluated alongside fluid dynamics.
- Measure target-device adapter selection, initialization, warmed and sustained frame times, memory usage, gesture latency and 4K export throughput. Report simulation resolution independently from output resolution; a 4K image does not demonstrate adequately resolved interfaces or droplets.
- Evaluate audio pre-scan, reusable templates, dynamic cue boundaries and first-pass computation. Cache only with reproducible settings, timing and state; a live gesture can invalidate subsequent cached states and requires defined replay and recovery.
- Evaluate adaptive resolution or allocating more computation near visible interfaces where the selected solver supports it. Check the visual and numerical error and its actual cost; do not assume an adaptive strategy or a specific speedup exists. FluidX3D states that it does not currently support adaptive mesh refinement, and current Taichi Metal sparse-SNode support must not be assumed.
- Evaluate live per-layer quality and resolution based on each layer's actual visible contribution, including opacity, masks and transmitted light through overlapping liquid layers. A layer behind another is not necessarily invisible. Reducing hidden color shading is distinct from reducing or pausing its fluid state: coupled phases can affect visible interfaces even when their own color is obscured. Any reduced state fidelity must preserve continuity and physically relevant coupling when a layer becomes visible again, with no reveal jump. None of the surveyed solvers has yet been verified to support this TSS-specific visibility policy; compare against a full-quality baseline and measure its cost and errors before enabling it.
- Configure live quality from measured capability and frame budgets, while retaining a separate offline high-quality budget. Benchmark against the same visual and motion criteria at each quality setting.
