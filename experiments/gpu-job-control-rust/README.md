# Rust GPU experiment control candidate

This isolated Rust program coordinates **cooperating** experimental GPU jobs through an OS advisory lock and a retained reservation directory, and can record `nvidia-smi` telemetry. It does not schedule unrelated applications, bound a GPU kernel or prevent GPU or driver failures. The candidate guarded a small Windows NVIDIA LuxCore `PATHOCL` job; see the [render evidence](../luxcore-native-study/output/windows-gpu-full-scene-photographic-20261119/EVIDENCE.md). It has not been integrated into TSS. It is **not a drop-in replacement** for the existing Python runner; see [equivalence.md](equivalence.md) before considering adoption.

This guard has not been validated for WSL GPU jobs. Microsoft's [WSL process architecture](https://github.com/microsoft/WSL/blob/master/doc/docs/technical-documentation/boot-process.md) describes Linux processes continuing independently of the lifetime of the invoking `wsl.exe`; containing `wsl.exe` in a Windows Job Object is therefore not sufficient evidence that the Linux GPU process is contained or terminated. A shared reservation and cross-boundary lifecycle must be designed and tested before using the same GPU from WSL and native Windows jobs.

The persistent sibling `<reservation>.guard` is locked for the full run or release. All participating Rust invocations must share exactly the same reservation path and this protocol. Older Python copies and unrelated GPU users must not be assumed to cooperate. Never replace the guard file while it may be in use. Reservation directory creation is atomic; failure, timeout, interruption, bad telemetry, surviving children, or unexpected errors leave it in place. A clean run releases it only after checking the contained process scope and telemetry shutdown.

The command is launched through this Rust executable's hidden bootstrap after it has joined a POSIX process group or a Windows Job Object. Windows jobs use `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. After a successful leader exit, Windows rechecks the Job Object for up to one second, bounded by the overall deadline; the reservation is released only if the active-process count reaches zero. A scope that remains nonempty fails and is terminated. The existing Unix path still checks immediately and does not have this Windows drain behavior. POSIX wrapper crash cleanup is not guaranteed. Commands must not deliberately escape the process group or dispatch independent external services. On a timeout, telemetry failure or surviving descendant, this candidate attempts to terminate the entire process scope. Signal handling and process teardown remain best effort; OS calls, a stuck driver or a submitted GPU command cannot be bounded by this tool.

## CPU-only verification

From this directory with Rust 1.87 or later, `cargo test` ran eleven tests on macOS and seventeen on Windows. Windows was tested using `windows-test.bat` on the same machine as the existing experiments; its MSVC and workspace paths are specific to that machine. Tests include active reservation, stale token, bad/slow telemetry, inherited-output handling, UUID/visible-idle preflight, optional progress timeout, descendant cleanup, and on Windows, wrapper death after a marker from the actual child. A real NVIDIA query with a CPU-only child also succeeded on the Windows host. No GPU process is launched by these tests. A later LuxCore job exercised the guard with actual GPU work, subject to the limits documented in its evidence; neither test establishes interoperability with the Python runner, reliability for deliberately escaping descendants, or device recovery.

## Interface

```sh
cargo run --bin tss-gpu-job -- run --reservation /path/to/reservation --timeout 120 -- /path/to/executable arg1
cargo run --bin tss-gpu-job -- run --reservation /path/to/reservation --timeout 120 --telemetry-csv /path/to/new.csv --interval 1 -- /path/to/executable arg1
cargo run --bin tss-gpu-job -- release --reservation /path/to/reservation --token TOKEN --confirm-stopped
```

Telemetry queries all NVIDIA GPUs with `nvidia-smi`: index, UUID, utilization, memory, temperature, and power. It rejects missing, non-numeric, non-finite and negative fields; 100% utilization is not considered an error. Samples are periodic and may miss peaks. Query failure terminates the command and retains the reservation. Each query has its own process scope and writes to a temporary file; on Windows the query deadline includes launch and up to one second of scope draining, after which a live scope fails closed; after query exit the reader rejects output larger than 1 MiB and limits what it reads. This is **not** a real-time cap on bytes written while the helper runs. A query that leaves a live descendant fails closed and its process scope is terminated. This stronger restriction is not established to be compatible with every NVIDIA driver installation. The CSV timestamp is Unix milliseconds, **not** the Python runner's ISO UTC timestamp; logs cannot be consumed interchangeably. `--smi-program`, repeatable `--smi-arg`, `--interval`, and `--smi-timeout` select and bound queries. The sampler is independent of the job deadline, but waiting for a telemetry subprocess to terminate may delay wrapper exit after the job has already been stopped.

`--require-idle` requires `--expected-nvidia-uuid UUID` and `--telemetry-csv`; within the reservation it requires exactly one matching sampled UUID, utilization no greater than `--idle-max-utilization` (default 5%), and no matching entries in `nvidia-smi`'s visible compute-process query. It rejects unavailable or malformed results. This is a sampled observation, **not proof that the GPU is idle**: graphics or unreported activity and noncooperating programs are not excluded, and the selected rendering device must be verified independently.

`--output-log NEWFILE` captures the command's stdout and stderr. `--progress-timeout SECONDS` optionally aborts if that file's length and modification time do not change for the specified duration; it requires `--output-log`. It is disabled by default because legitimate cold kernel compilation can be silent for minutes. File activity does not prove GPU progress; an overlong silent operation is not necessarily a hang. In all cases `--timeout` is the overall best-effort process deadline, not a GPU/driver recovery guarantee.

Recovery requires independent verification that all work and GPU activity are stopped. The token in `owner.json` must match, `--confirm-stopped` must be supplied, and a reservation without `outcome.json` additionally requires `--recover-stale`. A live compatible invocation keeps the guard locked and prevents release. A crash before owner creation may require manual inspection/removal after verification.

Implementation uses `fs2` (file lock), `clap` (command-line parsing), `csv`, `serde_json`, `uuid`, `wait-timeout`, `ctrlc`, `libc` for POSIX process groups, and Windows `windows-sys` Job Object APIs. Source and license details are recorded in `Cargo.lock`; retain each dependency's license when distributing.
