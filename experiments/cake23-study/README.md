# Cake23 Windows observation and guard study

The visual reference is Felix Woitzel's original [Turing fluid demonstration](https://cake23.de/turing-fluid.html), used as reference evidence rather than as TSS implementation. It combines a fluid-simulation component with one-component reaction-diffusion patterns. Its own page states the pattern texture is 1024×512 and the fluid simulation grid is 512×256. The page starts automatically on load, including WebGL drawing during initialization. It has not been opened during this study; no TSS output is implied by its behavior. The video's attribution and source remain separate from any TSS implementation, and no demo code or shaders are copied here.

## Windows process containment

On the Windows test laptop, NVIDIA's GTX 1650 Ti and Intel Iris Xe are visible. Chrome 157.0.8103.51 was present alongside an existing Chrome session. Tests used isolated profiles and the existing `experiments/gpu-job-control-rust` guard. No Cake23 page was loaded and no hardware GPU workload was dispatched.

A CPU-only PowerShell parent spawning a child was terminated by the guard's 8-second deadline; both recorded PIDs and the guard bootstrap were independently absent afterwards. A separate Chrome `about:blank` test used `--headless --disable-gpu --disable-software-rasterizer --disable-gpu-compositing` and a unique profile. A live process-tree snapshot recorded 13 Chrome processes and the guard bootstrap; all 14 recorded PIDs were absent after the 20-second deadline. Its reservation was released after verification. One sampled NVIDIA observation during the run was 0% utilization and 0 MiB; a sample is not proof of zero activity between samples.

A separate locally generated page tested WebGL renderer identification without drawing or loading external content. It used Chrome with `--disable-gpu --use-gl=angle --use-angle=swiftshader` and the existing guard with real NVIDIA telemetry. The first attempt failed closed on an NVIDIA telemetry descendant check. A second attempt returned a SwiftShader context and debug renderer string, but the guard failed closed with `descendants_remain` following browser exit. Reservations were retained until process/profile checks, then released. An isolated diagnostic build subsequently recorded one active Job Object PID at leader exit, and an empty Job Object 26 ms later. This is evidence of a contained short-lived process in that run; it does not alone establish its identity or prove every telemetry failure has the same cause.

The independently reviewed change has been applied to the existing guard; diagnostic and candidate diffs are recorded in `evidence/`. It rechecks actual scope membership for at most one second, bounded by the existing deadline, before accepting a successful leader or telemetry-helper exit. The main loop continues checking interruption and telemetry; surviving descendants still fail and trigger containment cleanup. This deliberately changes classification for descendants that exit during that bounded window and must be reviewed as a behavior change. The final guard passed 17 Windows tests and a CPU-only Chrome/SwiftShader probe with real NVIDIA telemetry. The one-second drain is Windows-only: Unix retains its earlier immediate check, and an existing numeric process-group ID reuse risk remains unresolved. macOS behavior has not been tested in this Windows-only pass.

## Constraints for any future hardware observation

Browser-wide GPU inventory is insufficient to prove which adapter a page's context uses. `WEBGL_debug_renderer_info`, when available, reports the renderer for the queried context, and the local SwiftShader probe confirmed that Chrome exposes it for that software context. It can be unavailable for privacy reasons. A hardware observation would require checking the actual page's context before allowing its code to draw, corroborating the identity against the adapter inventory, and failing closed on an unavailable, software, ambiguous or unexpected renderer. Context creation itself can touch the graphics driver, so containment and monitoring must already be active. No tested deterministic per-context adapter selection is claimed.

The page's own FPS counter counts animation-loop iterations; it is not evidence that frames were presented to a display. Browser compositor/presentation tracing is needed to establish delivered-frame timing, and any captured-video frame rate must be reported separately. A hard process deadline and periodic telemetry cannot bound individual GPU commands, prevent a graphics-driver crash, or prove all unrelated GPU applications are idle. Windows GPU Engine counters expose PID and adapter-LUID fields on this host, but correlating the LUID to the chosen physical adapter has not yet been verified. `nvidia-smi pmon -h` on this Windows installation documents per-process monitoring only for supported Linux systems; it is not assumed to work here.

Evidence includes guard output, the initial verification failure and corrected verification, diagnostic observations, candidate tests, and probe telemetry. Reservation release tokens in logs are redacted after release. `fixtures/` contains only local test/measurement code, not the reference's simulation or shaders.
