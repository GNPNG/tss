# LuxCore native source-build evidence

This study investigates the LuxCore 2.11.2 binary render-configuration serialization failure. It does not establish a serialization fix, real-time rendering, projector optics, or GPU safety.

- Source: upstream LuxCore commit `b872186`, expanded from the previously inspected sparse checkout in the isolated Windows study. Source build was started without altering the upstream serialization code.
- Official dependency version: LuxCoreDeps 2.2.3. `gh attestation verify -o LuxCoreRender --format json` returned one verified result for the upstream Windows archive. Its SHA-256 was `069a1eace7e8f192b07629d6318eca9e0ad970f8c7db39a0919b10eddc2345d0`; this matched the exact archive retrieved by the upstream build script.
- The upstream build check requires Conan 2.18 or later and CMake 3.29 or later. Conan 2.34.0 and wheel were installed only in the study-local build-tool environment. The upstream process ran in an isolated Conan home and output directory using the Windows MSVC developer environment.
- `prepare-upstream-windows.cmd` invokes upstream `make.bat deps`; dependency retrieval, Conan integrity checks, and generator setup completed. The missing `gh` warning in that invocation was addressed by the separate attestation check above.
- `build-upstream-windows.cmd` invokes upstream `make.bat luxcoreconsole` with `CMAKE_BUILD_PARALLEL_LEVEL=2`. After interruption, the same Ninja build and two MSVC processes remained active; it was not launched a second time. The active build has not yet been reported complete.
- NVIDIA telemetry after interruption sampled 0% utilization and 0 MiB; this is an instantaneous observation and not proof of device idleness. No GPU workload was dispatched for this source build.

Source inspection identified a value-versus-owning-pointer archive mismatch between FILESAVER's reference writer and loader, a dereference of an uninitialized merged-properties pointer, and failure to serialize the merged overrides. A potential external-scene lifetime issue requires runtime validation. Historical source from the original FILESAVER implementation wrote and read raw pointers symmetrically, but this alone does not establish compatibility with other releases. Preserve all previous failed test artifacts and validate ownership, both save overloads, override semantics, round trips, error handling and compatibility before calling a repair complete.

`serialization-candidate.diff` is an **unapplied, untested partial candidate** that initializes the merged configuration and serializes it. `git apply --check` against the pinned source passed. This addresses only two source findings; it does not repair the reference writer, prove archive compatibility or establish scene ownership. The pinned source tree was not modified during the baseline build.

`serialization-snapshot-candidate.diff` is a separate **unapplied, uncompiled and untested design candidate**. It additionally proposes an owning-pointer archive for the reference overload by creating a configuration snapshot with the existing no-Parse constructor, borrows the original scene only during synchronous saving, adopts a deserialized scene when needed, rejects missing/inconsistent scene pointers, and clears temporary overrides on archive exceptions. Its source context passed `git apply --check`; that is not a functional test. It requires independent review and actual pinned-LuxCore tests for object lifetime, aliasing, exception safety, format compatibility, pointer/reference overloads and scene non-mutation. In particular, the no-Parse constructor was originally described as deserialization-only, so using it for snapshots needs review. The full candidate supersedes neither the baseline nor the partial candidate until those tests pass.

Archive clarification: despite source comments referring to a portable archive, the pinned [`serializationutils.h`](https://github.com/LuxCoreRender/LuxCore/blob/b872186/include/luxrays/utils/serializationutils.h#L60-L63) aliases `LuxInputArchive` and `LuxOutputArchive` to Boost binary archives. The file wrappers add gzip compression. The earlier isolated reproduction used Boost binary archives but did not reproduce the complete LuxCore object, gzip wrapper, ownership or scene behavior; it is not an integration regression test. The stopped reproduction was not rerun.
