# Slide field and PixiJS study

This isolated engineering study connects genuine Basilisk-generated binary-liquid volume-fraction masks to PixiJS's sprite mask and gradient fill. It does not replace or alter the TSS application. Each registered layer has its own mask sequence; this study currently registers one layer. The fill is a simple visualization of the scalar field, not projector optics.

The 20 masks are from `basilisk-wsl-study/binary-liquid-output`: upstream centered Navier–Stokes, two-phase volume of fluid and surface tension, in an unforced periodic 2D domain, with both phases occupying the domain. They show an initial-condition relaxation, not a plate-gap model, calibrated merger, layer compression, inter-layer coupling or a physically based optical model. Solver times are simulation units. The fixed 4 FPS setting is a presentation choice, not measured performance.

On the Windows test laptop, `build-study.ps1` converts the solver's P6 grayscale PPM frames sequentially to lossless PNG with the installed FFmpeg, installs the pinned PixiJS, Vite and Playwright Core dependencies, hashes each PNG and the solver CSV into a manifest, and builds the study. The paths describe that machine and are not a cross-platform install procedure. Capture uses installed Chrome and a separate temporary profile; no browser binary is downloaded.

`capture.mjs` requires a renderer substring and verifies `WEBGL_debug_renderer_info` on the Pixi canvas before loading solver textures. Capture stores eight timestamped screenshots; their intervals are not a benchmark. A hardware capture must be launched under the reviewed Windows GPU job guard, with the known NVIDIA UUID and a fresh reservation, telemetry file, log and output folder. The browser renderer string identifies the context's reported adapter; it does not itself establish a UUID match. The guard's GPU idle check is a sampled observation, not a guarantee that other graphics workloads are absent.

On 2026-11-19, the first guarded hardware request selected Intel Iris Xe rather than the requested NVIDIA adapter and stopped before loading textures. A second attempt using PixiJS's documented `powerPreference: 'high-performance'` hint could not identify a WebGL 2 context using a second canvas query. The identity check was corrected to use Pixi's documented `app.renderer.gl`; a software SwiftShader capture then passed and a third guarded hardware request still reported Intel Iris Xe and stopped. The original second-query null is unexplained; the hint does not guarantee adapter selection. The NVIDIA hardware render remains unverified. Logs and NVIDIA telemetry are in `evidence/capture-hw-0*.log` and `evidence/capture-hw-0*-telemetry.csv`.

A fourth guarded hardware request added Chrome 157's Windows-supported process-local `--force-high-performance-gpu` switch. Pixi selected its Canvas renderer and the strict WebGL identity check stopped the study before masks loaded. NVIDIA telemetry recorded one 1% / 7 MiB sample, which does not establish a usable NVIDIA WebGL context. Pixi 8.23.0 source shows that its string `preference: 'webgl'` tries WebGL, then WebGPU, then Canvas; its WebGL support probe suppresses context exceptions. Existing browser logs do not establish the underlying WebGL initialization failure. No system GPU settings were changed.
